# V5 复习调度重设计（考试锚定的分档间隔）

- 日期：2026-10-15
- 前置调研：`docs/2026-10-15-anki备考模式调研.md`（Anki 机制对照）
- 影响模块：`app/services/unit_review_engine.py`、`app/routers/review_router.py`、`app/services/plan_engine.py`、`web/js/memo.js`、`app/schema.sql`
- 距初试：65 天（2026-10-15 → 2026-12-19）

---

## 1. 问题背景

### 1.1 现有调度（V3/V4）

`unit_review_engine.py` 采用固定 3 档间隔：

| 评分 | stage 变化 | 下次间隔 |
|---|---|---|
| 忘了 again | → 0 | 1 天 |
| 吃力 hard | 不变 | 3 天 |
| 秒答 good | +1（0→1、1→2） | 3 天 / 7 天 |
| — | stage ≥ 2 再秒答 | **毕业，永不再出卡** |

### 1.2 缺陷

1. **「毕业」让记忆在考前衰减**：一条单元的生命周期是第 0、3、10 天各见一次，之后**永不再出卡**。第 1 天学完的内容，最后一次复习在第 10 天——**考前 21 天内不会被复习到**（只有临近考试才首次学习的条目例外，而那不是设计意图，是巧合）。系统恰好在离考试最远的时候把内容"结业"。
2. **「吃力」是死档**：`HARD_DAYS = 3` 是常量，与 stage 无关，到后期三档几乎无区分度（详见 §9 范围边界，P0-2 另行处理）。
3. **容量与需求不匹配**：`review_n` 默认 60/天，而 5,349 单元 × 3 次曝光需 165 条/天。
4. **同日堆积**：`_plus(t, days)` 纯确定性，同期条目永远同日到期。

### 1.3 设计目标

**最大化 12-19 考试当天的得分**，而非抽象的长期保留率。由此推出两条原则：

- **考前新鲜度**：每条内容的记忆强度应在考试日达到峰值，即最后一次复习必须落在考期附近——而不是"毕业"后消失。
- **按分值分配容量**：复习容量有限时，曝光次数应与内容的分值贡献成正比，即 `tier`（第 X 梯队，`parse_content.py:66` 从调研文档解析）。

### 1.4 硬约束（算术事实）

容量不足以让全部内容在考前都"新鲜"：

| 过一遍全部 5,349 单元 | 所需日均 |
|---|---|
| 最后 7 天 | 764 条/天 |
| 最后 21 天 | 255 条/天 |
| 最后 35 天 | 153 条/天 |

**因此必须按梯队分档**——这是本设计的根本动因，不是优化选项。

## 2. 用户故事

- 作为备考者，我希望**考前两周打开「记」，看到的都是第 1 梯队和高频考点的内容**，而不是随机轮转的旧卡。
- 作为备考者，我希望**学得早的内容不会在考前"过期"**——早期学的光合作用不该比上周学的更模糊。
- 作为备考者，我希望**低价值章节不要占用我和高分章节同等的时间**。
- 作为备考者，我希望**每天的复习量是可控的**（约 30-40 分钟），而不是某天 1,200 条。

## 3. 方案概要

### 3.1 模块清单

| # | 模块 | 内容 | 层 |
|---|---|---|---|
| M1 | 考期相对阶梯引擎 | `next_interval` 计算式替换固定间隔表 | 后端 |
| M2 | 分档曝光次数 | 按 `tier` / 卡片类型决定 K | 后端 |
| M3 | 队列优先级排序 | 末段排序键改为 `(tier, stage, due)` | 后端 |
| M4 | 容量参数 | `review_n` 默认 **260**、clamp **100–300** | 后端 + 设置页 |
| M5 | 删除冻结规则 | 移除 `frozen` / `cap_days` 及其调用 | 后端 |
| M6 | 前端适配 | 按钮间隔标注改动态、范围面板提示 | 前端 |
| M7 | 验证脚本 | `scripts/simulate_schedule.py`，可复现本 Spec 的负载数字 | 工具 |

### 3.2 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 阶梯形状 | **考期相对几何铺开**（见 §4.1） | 固定倍增阶梯会让早期条目 26 天走完、考前陈旧（实测末段覆盖仅 23-31%）；考期相对式让每条内容自然收敛到考期附近 |
| 是否锚定考前 1 天 | **否** | 纯锚定会让 5,349 条全部落在同一天（模拟峰值 5,349）。改用「剩余时间按剩余次数几何铺开」+ 确定性抖动分散 |
| 分档依据 | `content.json` 的 `chapter.tier` | 是主人在调研文档中人工判定的优先级（第 X 梯队），比按分值百分位更准；且**已存在，无需迁移** |
| 分档粒度 | 章节级 | 单元不单独标注优先级；同章内所有单元同档 |
| K 是否落库 | **否**，从 content 现算 | 免迁移；tier 变更即生效 |
| 是否引入 FSRS | **否** | 见 §4.2 |
| 抖动来源 | item id 的 md5 取模 | 确定性、可复现、可测试；顺带承担 P1-1 的部分职责 |
| 容量分配策略 | **严格梯队优先**（排序即分配），**不设配额** | 配额制为喂低梯队会牺牲高梯队：实测配额 70/20/10 时第 1 梯队降至 82%，与「按分值分配容量」的目标冲突。代价是第 3 梯队被饥饿（实测 60%） |
| `review_n` 上限 | 180 → **260** | 上限卡的是**突发日**而非均值：180→260 时日均仅 129→155（仍低于批准预算），但第 2 梯队覆盖率 48%→101%（均由 `scripts/simulate_schedule.py` 实测） |

## 4. 技术选型

### 4.1 阶梯计算式（M1）

```
K          = 该条目的目标评分次数（含首次学习评分），由 §4.3 决定
stage      = 已完成的评分次数（首次学习评分后 stage = 1）
k_remain   = K - stage              # 还剩几次复习（含即将安排的这一次）
jitter     = 1 + md5(item_key)[:8] % 21      # ∈ [1, 21]，确定性
R          = days_left - jitter     # days_left = EXAM_DATE - today

若 stage >= K 或 R < 1  → 毕业（stage 置为 K，行保留）
否则                     → 下次间隔 = max(1, round(R / (2^k_remain - 1)))
```

**性质验证**（`days_left` 以天为单位，`item_key` = `point_id#idx` 或 `card_id`）：

| 场景 | 计算 | 结果 |
|---|---|---|
| 第 0 天学，T1（K=4），jitter=10 | k=3→54/7=8；k=2→46/3=15；k=1→31 | 复习落在第 8、23、54 天 |
| 第 30 天学，T1（K=4），jitter=5 | k=3→29/7=4；k=2→25/3=8；k=1→17 | 复习落在第 34、42、59 天 |
| 第 0 天学，T3（K=2），jitter=7 | k=1→57 | 复习落在第 57 天 |

- **末次复习恒落在考前 `jitter` 天**（1–21 天窗口内），由 id 哈希分散，不会全部撞在一天。
- 早期条目的阶梯自动拉长（首次间隔 8 天而非 1 天），自然铺满到考期。
- 无需 `EXAM_DATE` 之外的特判。

### 4.2 为何不引入 FSRS

- V3 Spec 已将「FSRS 全量算法、期望保留率可调」列为**非目标**，本设计延续该决定。
- 调研结论支持：Anki 官方 PR #4391「Enable FSRS by default」于 2026-02-12 关闭未合并，理由为「FSRS-6 默认参数不优于 SM-2」；FSRS 至今仍是 opt-in。其优化器需要数百条以上复习历史才能拟合，而本系统 `unit_reviews` 表尚为空。
- 本设计吸收了 FSRS 的两条核心思想——**目标时间锚定**与**按分值分配容量**——但用可解释的闭式公式实现，无参数维护面。
- 未来若接 FSRS，`stage/due` 结构可平滑迁移（V3 Spec §4 原话）。

### 4.3 曝光次数 K（M2）

| 内容 | 数量 | K | 调度复习次数 (K−1) |
|---|---|---|---|
| 背题卡 | 165 | 6 | 5 |
| 第 1 梯队单元（tier=1） | 2,281 | 4 | 3 |
| 第 2 梯队单元（tier=2） | 2,045 | 2 | 1 |
| 第 3 梯队单元（tier=3） | 1,023 | 2 | 1 |
| 无 tier（缺省） | — | 2 | 1 |

**理由**：背题卡是主观题、单条分值最高且数量仅 165，长阶梯几乎免费；第 3 梯队 K=2（而非 1）把「只阅读」升级为「检索练习」——调研引 Dunlosky et al. 2013 指出练习测试是高效用技术、重读是低效用。

> **第 3 梯队的 K=2 是「尽力而为」**：因末段容量超订 + 严格梯队优先，实测只有 60% 的第 3 梯队条目能拿到考前复习（§6.1）。K=2 保证的是「进入调度」，不保证「被调度到」。这不是缺陷，是有意的优先级取舍。

## 5. 数据模型

**不新增表、不新增列、不需要迁移。**

- `unit_reviews(point_id, idx, stage, due_date, updated_at)` 语义扩展：`stage` 从「0/1/2/3 阶段」变为「已完成的评分次数」，`stage >= K` 表示毕业。
- `card_reviews(card_id, stage, due_date, updated_at)` 同上。
- **既有数据兼容**：V3/V4 遗留行的 `stage ∈ {0,1,2,3}` 在新语义下即为「已完成 0–3 次评分」。因为 T1 的 K=4、其余 K=2，遗留的 stage=3 行（旧「毕业」）在 T1 会被视为还差 1 次、在 T2/T3 视为已毕业。**行为可接受**，但需在实现时用一次性脚本或直接接受（数据量近零，见 §8 风险 R3）。
- `daily_log.review_n`、`settings.review_n` 沿用，默认值由 60 改为 **260**（clamp 100–300）。

## 6. API 设计

### 6.1 `GET /api/memo/queue`（扩展）

- 新增返回字段：
  - 每个 item 增加 `tier: int`、`k: int`
  - `next` 字段由「静态三档天数」改为**按当前 stage 计算的三档候选值**（仍是 `{again, hard, good, graduates}`，但数值随 `days_left` 与 `stage` 动态变化）
- **排序变更**：`_memo_sort_key` 由 `(stage, due_date, point_id, kind, tail)` 改为 **`(tier, stage, due_date, point_id, kind, tail)`**
  - 理由：末段容量不足时，排序规则**就是**分配策略。让第 1 梯队优先拿到复习机会。
  - 跨科轮转交错（`_assemble` 的 round-robin）**保持不变**。
  - **已知代价（实测）**：末段容量超订——最后 21 天有 5,514 条各想要一次复习，容量为 `review_n × 21`。严格梯队优先意味着**低梯队会被饥饿**。模拟实测（学习期 45 天、上限 260）：第 1 梯队 126%、第 2 梯队 101%、**第 3 梯队 60%**。这是有意的取舍，不是缺陷；若改为配额制，第 1 梯队会掉到 82%，与"按分值分配容量"的目标冲突。
- 显式范围（`subjects`/`chapters`/`points`）仍不截断；`quick=due` 仍按 `review_n` 截断。

### 6.2 `POST /api/unit_review` / `POST /api/card_review`（接口变更）

- 两者需**新增 `tier` 输入**（由前端从本地 content 索引带出），或后端自行 `find_point` 反查 tier。
  - **选择**：后端反查。`content.find_point()` 已能拿到章节，`iter_chapters` 可建 `point_id → tier` 映射并在 `content.load_content()` 侧缓存。避免前端传参被篡改导致调度不一致。
- 三档评分的 stage/due 推进按 §4.1 计算式，替换现有 `_schedule`。

### 6.3 删除

- `GET /api/review/queue` 的 `frozen_graduation` / `days_left` 字段语义调整：`frozen_graduation` 删除（冻结概念不存在），`days_left` 保留（前端展示用）。

## 7. 验证标准

### 7.1 单元测试（重写 `tests/test_unit_review_engine.py` 矩阵）

1. **阶梯计算式矩阵**：`(stage, K, days_left, jitter)` → 间隔天数；覆盖 k_remain = 3/2/1/0 与 R < 1 边界。
2. **毕业语义**：`stage >= K` 不再出卡；行保留。
3. **抖动确定性**：同一 `item_key` 多次调用 jitter 恒定；不同 key 分布落在 [1,21]。
4. **分档**：tier=1/2/3 与 card 分别取到 K=4/2/2/6；无 tier 缺省 K=2。
5. **排序**：同 due 下 tier 小者在前；跨科轮转交错不被破坏。
6. **容量**：`review_n=260` 截断、`due_total` 保留、显式范围不截断。
7. **旧数据兼容**：stage=3 的遗留行在 T1 仍出卡、在 T2/T3 已毕业。

### 7.2 模拟验证（M7，必交付）

`scripts/simulate_schedule.py`：输入 content.json 与参数（K 表、CAP、学习期天数），输出：

- 日均 / 峰值 / 顺延次数
- 各梯队「考前 21 天覆盖率」与「走完阶梯比例」
- 逐日负载曲线（可导出 CSV）

**验收阈值**（学习期 45 天、CAP=260；括号内为定稿前的模型实测值）：

| 指标 | 目标 |
|---|---|
| 第 1 梯队考前 21 天覆盖率 | ≥ 95%（实测 126%） |
| 第 2 梯队考前 21 天覆盖率 | ≥ 90%（实测 101%） |
| 第 3 梯队考前 21 天覆盖率 | ≥ 40%（实测 60%——**有意饥饿**，见 §6.1） |
| 日均 | ≤ 180（实测 155） |
| 峰值 | ≤ CAP（实测 260） |

> 覆盖率统计的是「考前 21 天内的复习**次数**」，故第 1/2 梯队会超过 100%（部分条目该窗口内被复习多次）。

> **注意**：M7 脚本是实现的交付物，其输出为准。若第 1/2 梯队达不到阈值，优先下调 `K_BY_TIER` 中低梯队取值，而非再提高 CAP（CAP 主要影响突发日，不影响均值）。

### 7.3 浏览器自验（金路径）

今日页 →「记」→ 今日到期队列 → 观察到：

- 第 1 梯队条目排在前面
- 卡片按钮标注的间隔随 stage 递增且随 `days_left` 收缩
- 完成一次评分后 `next` 数值变化符合预期

## 8. 风险点

| # | 风险 | 应对 |
|---|---|---|
| R1 | **设计假设「45 天内学完全部 5,349 单元」= 119 条/天首次学习 + 164 条/天复习 ≈ 283 条/天**，该学习速度从未被验证（当前库近乎为空） | M7 脚本支持调整学习期天数；若实际学得慢，末段覆盖会低于 90%，届时下调低梯队 K |
| R2 | 末段容量长期满载，「今天没做完」成为常态 | 这是设计使然；今日页文案需明确「未完成会顺延，不会丢失」 |
| R3 | 旧数据（stage=3）在新语义下行为变化 | 数据量近零（`unit_reviews` 表尚未在真实库建立），选择直接接受；若已有数据则先跑一次清零 |
| R4 | 抖动与 Anki fuzz 语义不同（本设计用 jitter 分散末次，而非按间隔百分比抖动） | 二者目的不同：jitter 保证末次落在考期窗口内；完整 fuzz（P1-1）仍待后续实现 |
| R5 | **第 3 梯队被饥饿**：末段容量超订，严格梯队优先下第 3 梯队实测仅 60% 拿到考前复习 | 已量化并接受（§6.1）。显式范围模式（选章节）不受排序与截断影响，用户可主动刷低梯队；若需提高，改配额制会牺牲第 1 梯队（实测降至 82%） |
| R6 | `review_n` 上限提到 260 后，最重的一天约 52 分钟 | 均值仍为 156 条（≈31 分钟），低于原批准预算；上限可在设置页随时下调 |

## 9. 范围边界

### 9.1 本次不做（后续 P0-2 / P0-3 / P1 / P2）

| 项 | 说明 |
|---|---|
| **P0-2 ease factor** | 「吃力」仍是 `stage 不变 + 间隔减半`，未引入按条目难度记忆。加 `ease` 列需 schema 迁移，另行处理 |
| **P0-3 当日重学** | 忘了仍直接推到明天，未实现 relearning steps |
| **P1-1 完整 fuzz** | 仅用 jitter 分散末次；按间隔百分比的抖动未实现 |
| **P1-2 leech** | 未做 |
| **P1-3 记住率指标** | 未做 |
| **P2-2 迟延补偿** | 未做 |

### 9.2 明确删除

- V3 的「考前 ≤21 天压缩到 ≤3 天、≤7 天压到 1 天」规则 → 由考期相对阶梯自然实现，删除 `frozen()` / `cap_days()` 及 `frozen_graduation` 字段。
- V3 的「冻结毕业」（考前不再毕业）→ 删除；毕业由 `stage >= K` 单条件决定。

### 9.3 不变更

- 跨科轮转交错（`_assemble`）
- 队列四来源合并逻辑（到期单元 / 到期考点展开 / 到期卡 / 范围集合）
- 显式范围不截断
- 快捷集合（`due`/`today_look`/`fav`/`hot`）与筛选（`due`/`fav`/`weak`/`hot`）
- 「看」页为纯阅读检索，「测」页不含背题卡

## 10. 附录：与既有模块的关系

- **与 V3「记忆增强」**：V3 建立了单元级调度与三档评分，本设计替换其调度核心，保留其数据表与交互形态。
- **与 V4「记」模块**：V4 建立了统一队列与翻转卡 UI，本设计不改 UI 结构，只改排序与间隔数值来源。
- **与 `plan_engine`**：`days_left()` 已是本设计的核心输入；`EXAM_DATE` 仍为唯一锚点。
- **与调研文档**：本设计对应调研 §7 的可借鉴点 #7（间隔上下限）、#9（目标保留率反推间隔的思路）、#12/#13（队列排序），未采纳 FSRS 全量实现（见 §4.2）。
