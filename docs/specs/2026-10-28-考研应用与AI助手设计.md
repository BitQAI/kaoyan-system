## 一、问题背景

元数据侧已完成：四科知识点、单元、卡片、图示、关联、朗读稿全部就绪，`py 知识点元数据/scripts/pipeline.py --check` 全绿。应用本体一行代码都没有（原 `kaoyan-app/` 目录已不存在）。

用户的核心学习动作是**「看 → 记 → 听」**三个视图。三者的共同断点：**读不懂就卡住**。现有资料是教材式的中性陈述（`explain` 中位 196 字，`exam` 是分号串起来的多段结构），懂了的人读着高效，没懂的人读三遍还是没懂——缺的是类比、因果链、和「为什么是这样」的重讲。

因此本期要做两件事，一次交付：

1. **把应用本体建起来**（看 / 记 / 听 三视图 + 服务端存储）；
2. **加一个常驻 AI 助手**：在任何视图遇到不懂的点，随手唤起，让 AI 把同一个知识点用更详尽、更生动的方式重讲一遍，并保留按知识点归档的问答历史。

## 五、数据接入

### 5.1 产物形态：直接用 SQLite，不产 `data/web` 静态包

决策简报的 M0 假设「前端直接读静态 JSON 包」。既然服务端已定，**改为导入 SQLite，前端全部走 API**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 静态包 `data/web/`（简报原方案）** | 前端可脱离后端 | 与 DB 导入重复一套转换；关联/检索仍要后端；两处数据易漂移 |
| **B. SQLite + API（本设计）** | 单一数据源；检索、关联、进度天然在库里；首屏只拉 manifest | 无后端就不能跑（本项目不需要） |

**选 B。** `data/web` 不再产出。风险：首屏依赖后端，本地部署可接受。

### 5.2 导入契约

源：`知识点元数据/subjects/<sid>/<sid>.json`（`ky-point/3.0`）。只读，不改。

| 目标表 | 来源 | 关键处理 |
|---|---|---|
| `subject` | 顶层 `subject/name/score/status` | — |
| `chapter` | `chapters[]` | `tier`、`weight_center`、`weight_range`（可为 null）、`weight_basis` |
| `point` | `points[]` 除 `cards/units/media` | `exam_evidence` 拆成 `evidence_level/basis` 两列 + `evidence_sources` JSON |
| `unit` | `points[].units[]` | 主键 `(point_id, idx)`，idx 从 1 起 |
| `card` | `points[].cards[]` | `card_id` 全局唯一；`answer_points`/`unit_refs` 存 JSON |
| `media` | `points[].media[]` | `svg` 原样入库，**导出时服务端 sanitize** |
| `point_relation` | `prerequisites/related/confusables` | 三类统一存 `(point_id, kind, target_id, name, distinction)`；`confusables` 可无 `target_id` |
| `listen` | `points[].listen` | `script` 整段入库；`audio` 恒 `pending`，前端忽略 |

导入脚本 `backend/scripts/import_meta.py`：**幂等**（先清后插，单事务），跑完打印各表行数，与源 JSON 计数对齐。

### 5.3 检索索引

```sql
CREATE VIRTUAL TABLE point_fts USING fts5(
  point_id UNINDEXED, title, point, keywords, explain,
  tokenize='trigram'
);
CREATE VIRTUAL TABLE card_fts USING fts5(
  card_id UNINDEXED, point_id UNINDEXED, question, answer, answer_points,
  tokenize='trigram'
);
```

`trigram` 已在本机 sqlite 3.53.1 实测可用（子串「生命活动」命中整句）。用外部内容表（`content=''`）避免正文双份。

## 六、AI 助手（本设计的核心）

### 6.1 一句话

**全局悬浮球 + 三视图「问 AI」入口 → 带当前 `point_id` 提问 → 后端用「当前点全文 + 会话历史 + FTS 召回 + 溯源分句」组装上下文 → LLM 流式重讲 → 按会话与知识点双维度归档。**

### 6.2 与 fk 的差异（必须明确的四处）

| # | fk 做法 | 本项目 | 为什么 |
|---|---|---|---|
| 1 | 系统提示「只能基于提供的资料回答，不确定就明说」 | **允许补充讲解**：资料内内容照讲，资料外的类比/背景标注「补充说明」 | 用户要的是「更详尽生动」；严格封闭会退化成复述原文，触碰反目标 |
| 2 | 单轮无状态，每次重新检索 | **多轮**：带上当前会话最近 6 条消息 | 「更详尽一点」「再举个例子」天然是多轮追问 |
| 3 | `chat_logs` 单表，按 `entry_id` 在 Python 侧过滤 | **`conversations` + `messages` + `message_points`**，SQL JOIN + 索引 | 按点反查历史不受 200 条上限约束；支持会话列表页 |
| 4 | 切知识点即清空对话 | **切点即新建会话**，旧会话留在历史里 | 用户可能回头接着问；fk 的清空会丢上下文 |

UI 形态、交互细节（悬浮球拖拽、长按、双击复位、流式打字、历史折叠、回填问题）**照搬 fk**，用户已确认满足需求。

### 6.3 入口

| 位置 | 触发 | 携带 |
|---|---|---|
| 全局 | 悬浮球（可拖拽，位置 localStorage 持久化） | 无 → 通用提问 |
| 看 · 点详情 | 「问 AI」按钮 | `point_id` |
| 记 · 翻卡 | 卡片右上角「问 AI」 | 所属 `point_id` + 当前 `card_id` |
| 听 · 朗读中 | 「问 AI」按钮 | 当前 `point_id` |

点详情与卡片上的「问 AI」旁显示该点历史条数徽标（fk 同款，`ai-asked` 事件即时 +1）。

### 6.4 上下文组装（`assistant.build_context`）

分层，按 token 预算裁剪：

| 层 | 内容 | 预算 |
|---|---|---|
| L0 | 系统提示（见 6.5） | 固定 |
| L1 | **当前知识点全文**：`point` / `title` / `explain` / `exam` / `keywords` / `units[]` / `cards[]`（question + answer_points）/ `listen.script` / `confusables` / `media[].alt` / `exam_evidence.level + basis` | ≤3000 字 |
| L2 | **会话历史**：本会话最近 6 条消息（user + assistant） | ≤2000 字 |
| L3 | **FTS5 召回**：用问题原文 MATCH，bm25 取 ≤5 个其它点，只给 `point + title + explain` 摘要 | ≤1500 字 |
| L4 | **溯源节选**：当前点 `source.ref` 解析出的原文分句 | ≤800 字 |

L1 超预算时的裁剪顺序：`units` 截断 → `cards` 只保留 question → `exam` 截断。**永远不裁 `explain` 与 `title`**。

L4 复用元数据侧已验证的 locator 配方（`知识点元数据/scripts/check_locator.py`，524/524 逐字一致）：`source.ref` 形如 `p4-2#绪论/p[0]/split[0]`，=`源文件#section/p[段]/split[分句]`。源 HTML 在仓库根，按 `source.file` 定位。实测分布：**524 点 `kind=html`**（指向 `2027考研_四科知识全景与章节权重.html`）、**14 点 `kind=syllabus`**（指向 `《812植物生理学》考试大纲.pdf`，locator 不适用）。

> 14 个 syllabus 点没有可解析的 HTML 段落，L4 改为取 `exam_evidence.basis`（含考纲条款名）作溯源说明，不报错。

> **取整段，不取分句**：`split[M]` 那一片就是该点的 `point` 字段本身，单独取出来与 L1 完全重复、零增益。L4 应取该 `<p>` 的**整段原文**（各分句按 `；` 还原），这才是「这一点在原始资料里的完整语境」。（`mech[M]` 型 ref 取对应 `<p class="mech">` 整段。）

### 6.5 系统提示词（本设计的灵魂）

```
你是考研辅导老师，正在给一名已经读过教材式知识点条目、但没读懂的学生重讲。

要求：
1. 先用一句「人话」说清这是什么，不要复述原定义。
2. 给一个具体类比或生活场景，让抽象概念有画面。
3. 讲清因果链：为什么是这样、前后怎么串起来。
4. 回到考试：这个点怎么考、最容易被扣分的地方在哪。
5. 400–800 字，Markdown 小标题 + 必要时用列表，适合手机阅读。

事实纪律：
- 提供的资料是权威口径，与资料冲突时以资料为准。
- 资料未覆盖的背景知识可以补充，但要用「补充：」标出。
- 不得编造考纲条款或条款号。资料里 exam_evidence.level 为 inferred 的，说「这是推断」，不说「考纲要求」。
- 不确定就直说不知道，不要圆场。
```

### 6.6 SSE 协议

fk 只发 `delta`，失败时前端会一直转圈。本项目补全三类事件：

```
data: {"type":"delta","delta":"…"}
data: {"type":"done","message_id":123,"related_point_ids":["2040101"]}
data: {"type":"error","message":"…"}
```

前端据此区分「生成中 / 完成 / 失败」；`AbortController` 中断时服务端停止生成并**不落库**（或落已生成部分，见 6.7）。

### 6.7 落库与历史

```sql
conversations(id TEXT PK, title TEXT, point_id TEXT, created_at, updated_at, msg_count INT)
messages(id INTEGER PK, conversation_id TEXT FK, role TEXT, content TEXT,
         related_point_ids TEXT, source_refs TEXT, model TEXT, created_at)
message_points(message_id INTEGER, point_id TEXT, PRIMARY KEY(message_id, point_id))
CREATE INDEX idx_msgpt_point ON message_points(point_id);
CREATE INDEX idx_msg_conv ON messages(conversation_id, id);
```

写入时机：流结束一次性写 user + assistant 两行；中断时只写已生成部分并标记 `truncated=1`。标题取首问前 24 字。

历史读取：

| 场景 | 查询 |
|---|---|
| 抽屉内「历史问答」 | `message_points` JOIN `messages` WHERE `point_id=?`（不靠 JSON LIKE，避免 `2040101` 误配 `20401010`） |
| `/history` 会话列表 | `conversations` 按 `updated_at DESC`，附首问标题与消息数 |
| 会话详情 | `messages` WHERE `conversation_id=?` ORDER BY id |

### 6.8 前端交互（照搬 fk + 四处调整）

- `AiFab`：54px 悬浮球，长按 450ms 拖拽，双击复位，`localStorage` 持久化位置；点击开关面板。
- `AiChat`：手写 SSE 解析、打字机占位、逐字 Markdown 渲染（`lib/md.ts` 先转义后渲染）、复制回答、停止生成、历史折叠 / 全部展开收起 / 回填问题。
- 快捷问法（有 `point_id` 时）：`换个更通俗的说法讲` / `举个生活里的例子` / `讲清它和易混概念的区别` / `这个点在真题里怎么考`。
- 关闭面板不结束会话（与 fk 不同）：再次打开可继续；**切换知识点才新建会话**。

### 6.9 故障降级

- 无 key / 网络异常：返回「AI 助手未配置或暂时不可用」，不抛错、不影响看记听。
- LLM 超时：前端 90 秒无首字则显示重试。
- 检索为空：只带 L1 + L2，照常作答。

### 7.1 看

- 章节树：科目 → 模块 → 章，按 `tier` 与 `weight_center` 排序，显示权重区间与 `weight_basis`（204 需显式提示「人工估计，合计 116≠100」，不归一化）。章 → 点列表 → 点详情，三级导航（原型没有这层，是本期新增）。
- 点详情顺序沿用原型 `renderStudy()`：标题 → 考点解析（`explain` 按句 2 句成段 + `.key-line` 强调）→ 图示 → 怎么考（`exam` 按 `。！？` 成 `<li>` 列表）→ 关键词 chips → 本题（question / 答案 / answer_points / 解析）。
- **不做标签识别**：`exam` 里约七成段落无显式前缀，且实际标签（「常考产物预测题」「阅读 A」「解题步骤」…）远超任何白名单；强行识别会误切。按句成列表即可读，也与原型一致。
- 证据徽章与关联区接在点详情末尾（原型无此两块）：徽章点开显示 `basis`，101/204 显示 `clause`；关联区按前置/相关/易混分组，空组不显示。
- 记号渲染 `lib/notation.ts`（原型未覆盖）：39 条显式映射（`K_b→K<sub>b</sub>` 等）+ 默认规则 `/([A-Za-zΨΔ])_([A-Za-z0-9]+)/` + 白名单防误伤（`S_EAr` 等），**必须有回归测试**。
- 图示：服务端 sanitize（只允许 `svg/path/rect/circle/text/g/polygon/polyline/line/defs/clipPath/marker`，禁 `script/foreignObject/on*`）；同页 ≤6 张展开，进入视口再注入（40KB–260KB/章的体积下这是必需的）。
- 检索：FTS5，结果分「知识点 / 卡片」两组，默认先出知识点。

### 7.2 记

- **主形态：卡片自测**（3171 张），交互照搬原型 `renderMemo()`：3D 翻转、空格翻面、`1/2/3` 评分、本组完成统计。
- 翻卡：`question` → 翻面 `answer` → 展开 `answer_points`（可逐条勾选）→ `analysis`；`unit_refs` 回指「这张卡考的是第几条 unit」。
- **单元自测本期只做「浏览 + 手动标记已掌握」**，不接调度。理由：5293 条 unit 需要第二套评分交互，而 unit 的内容与所属点的 `explain`/`units` 高度重叠；先把卡片自测跑顺，看实际使用后再决定。
- 三档评分：`秒答 / 吃力 / 忘了`；SM-2 简化。
- **`difficulty` 缺失的处理**（实测：812 完整，315 缺 1128/1191、101 缺 797/810、204 全缺）：缺省取 **2**，再按 `card_type` 微调（`定义`/`记忆` −1，`综合`/`论述` +1），夹在 1–3。**不回写元数据**。
- 落库：`card_progress(card_id, stage, ease, interval, due_at, lapses, reviews, last_result, updated_at)`。
- 刷新后进度不丢（服务端 SQLite）。
- 卡片上「问 AI」带 `point_id`。

### 7.3 听

- 朗读单位 = 一个点的 `listen.script` 整段，交互照搬原型 `renderListen()`：朗读 / 停止按钮、播放状态、波形动画、可展开的朗读稿（按 `设问：/答案：/解析：` 分块）。
- Web Speech API `SpeechSynthesisUtterance`，`lang=zh-CN`，默认 `rate=0.95`（原型取值）；提供 0.75 / 1.0 / 1.25 三档。
- 逐句高亮为**可选增强**，放 P6；原型未做，不阻塞验收。
- 断点续听：`listen_progress(point_id, updated_at)` 记录「已听」，不记句内位置（语速可调时句内位置无意义）。
- 队列排序：未听优先 → 次数少优先 → 久未听优先 → priority → 章 tier。
- iOS Safari 限制：需用户手势触发首次播放，切后台会停——UI 上不承诺后台播放。
- 「问 AI」带当前 `point_id`。

## 九、数据模型（运行时表）

```sql
point_progress(point_id PK, read_at, listen_at)
unit_progress(point_id, idx, mastered_at, PK(point_id, idx))   -- 本期只标记已掌握，不调度
card_progress(card_id PK, stage, ease, interval, due_at, lapses, reviews, last_result, updated_at)
listen_progress(point_id PK, listen_count, updated_at)
settings(key PK, value)                                        -- exam_date / daily_quota
```

全部通过 **Alembic** 建表与演进（不照搬 fk 的手写 `ALTER`）。模型与迁移同一次提交。

**Alembic 与原生 sqlite3 的衔接**：Alembic 本身依赖 SQLAlchemy，因此 `.venv` 里必然有它。`app/models.py` 用 **SQLAlchemy Core `MetaData` + `Table`** 声明全部表（只作迁移源与 `target_metadata`），运行时仍用原生 `sqlite3`（`db.connect()` 与 fk 同款参数）按同一 DDL 建表。这样 `alembic check` 有可比对的元数据，CLAUDE.md 的提交纪律才落得了地。若两者出现漂移，以迁移为准并补测试比对。

## 十一、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| **LLM key 未落位** | 无 `.env` 时 AI 全哑 | 复制 fk 的 `.env` 中 `DEEPSEEK_*` / `OPENCODE_*` 到本项目 `.env`（gitignore，600 权限），不打印内容；后台 `/api/health` 报 `ai_configured` |
| **上下文过长** | 538 点全文 + 历史 + 召回超预算，回答变慢变贵 | 6.4 的预算与裁剪顺序；超限优先砍 units/cards |
| **AI 说套话** | 回答像百科复述 | 提示词强制「类比 + 因果链 + 怎么考」三段；抽检不达标就改提示词，不改架构 |
| **SVG 注入** | `media[].svg` 是字符串注入面 | 服务端白名单 sanitize + 前端只 `dangerouslySetInnerHTML` 已净化串 |
| **首屏体积** | 一章 40–260KB 正文 | 只拉 manifest + 单章；图示懒加载 |
| **iOS TTS 限制** | 切后台停、需手势 | 文案明示；不做后台播放承诺 |
| **Alembic + 原生 sqlite3** | 无 ORM，迁移需手写 `op` | fk 的 `db.py` 建表 SQL 作为 `op.execute` 源；模型改动先写迁移 |
| **204 证据偏弱** | 6 verified / 45 inferred | 徽章中性色，不出现「考纲明文」措辞；提示词同步约束 |

## 十二、分期与交付顺序

AI 助手是用户最关心的功能，**排在「看」之后、「记」之前**——它只需要点数据就能工作，而记/听能在其上线后各自接上入口。

| 阶段 | 内容 | 交付物 | 可独立使用 |
|---|---|---|---|
| **P1 骨架 + 数据** | `backend/` 骨架、Alembic、`models.py`、`import_meta.py`、`/api/manifest` `/api/points/{pid}`、Next 骨架 + 设计令牌 + 底部导航 | 数据库 + 首批 API + 空壳前端 | ✅ API 可查 |

| **P3 AI 助手** | `ai.py`、`assistant.py`、SSE、conversations/messages、AiFab/AiChat、历史、`/history` | 常驻问答 | ✅ 能问能回看 |
