## 一、现状分析

### 1.1 数据流全景

```
master_eaxm/*.html（6 份调研文档，只读）
  │  scripts/parse_content.py        ← 唯一的"知识"来源
  ▼
content/content.json  ── 内容真源（运行时唯一读取）
  │  gen_notes.py  → note / exam / keywords
  │  gen_units.py  → units[]（原子知识单元，LLM 拆分）
  │  gen_cues.py   → cue
  │  validate_content.py --merge → quiz[] / cards[]（来自 content/quiz/*.json）
  ▼
SQLite data/kaoyan.db  ── 纯运行时状态（进度/调度/统计/收藏/错题/AI 会话）
```

关键事实（代码依据）：

| 事实 | 依据 |
|---|---|
| 内容真源是 `content.json`，DB 只存状态 | `app/content.py:12-17`（`load_content` 只读 json + `@lru_cache`） |

### 1.2 知识点的真实粒度（最关键的事实）

**知识点 = HTML 中一个 `<p>` 段落内，用中文分号 `；` 切出的每一个分句。**

不是 `<li>`，不是 `<p>` 本身。`<li>` 只出现在大纲侧，用于打标签和覆盖度校验，不产生知识点。

抽取规则（`scripts/parse_content.py:38-53`）：

```python
def split_points(text, chap_id, subject):
    merged = []
    for raw in [p.strip() for p in re.split(r"[；;]", text) if p.strip()]:
        if merged and len(raw) < 5:          # 碎片并入前一点
            merged[-1] = merged[-1] + "；" + raw
        else:
            merged.append(raw)
    ...
    "id": f"{chap_id}-{i:02d}"              # id = 章序号-章内序号
```

其中 `text` 来自 `text_of()`（`parse_content.py:24-27`），**必须先做 HTML 实体反转义再切分**——`&lt;` 中的 `;` 若不先反转义，会把实体切成两半（本次已实测复现）。

源结构按科目分三种：

| 科目 | 源 section | 容器 | 点数 |
|---|---|---|---|
| 812 | `p4-2` | `<div class="chapter">` → `<p>` + `<p class="mech">` | 107 |
| 315 | `p3-4` | `<div class="topic">` → `<h3>` + `<p>` | 198 |
| 101 | `p1-4` | `<div class="topic">` → `<h3>` + `<p>` | 155 |
| 204 | **无 HTML** | Python 硬编码常量 `CHAPTERS_204`（`parse_content.py:188-256`） | 51 |

## 二、参考框架的借鉴与改造

法考框架的核心方法论（值得直接继承）：

1. **单表逐条 + 字段表定规格**（类型 / 必填 / 约束 / 示例 四要素）
2. **受控词表与 ID 前缀绑定**（`科目 ↔ 前缀 ↔ 子科目范围`）
3. **md 人审真源 + JSON 机洗真源，单向流水线**（md→json→视图，杜绝两套数据漂移）
4. **front matter 声明 status / batch，调度器只消费 final**
5. **硬错误 E 码阻断 + 软警告 W 码人工复核** 两级校验
6. **可空字段严格受限**，其余必填
7. **结构化溯源串**（`类型:出处#定位`，`;` 分隔）

需要改造之处（考研域与法考域的结构差异）：

| 法考框架 | 考研实际情况 | 本次改造 |
|---|---|---|
| 2 级：`科目 > 子科目 > 条目` | 3 级：`科目 > 章 > 知识点`（章有独立的权重、梯队、标题） | **章节单独建表**，不把章级字段平铺到每行 |
| 锚点句 = 案例/场景句 | 锚点句 = **考点原文句**（已是标准答案，非案例） | 保留「锚点」概念并更名为 `point`；**新增 `title`**（现 `cue`）作检索/卡面 |
| 法条定位（机器引用） | 315 有公式/常数，812 有名解/简答/论述题型 | 升为**科目扩展字段**，不进核心表 |
| 无「抽取位置」溯源概念 | 考研 HTML 章节结构明确，可精确到分句 | **新增 `locator` + `merged_from`**，精确到分句级 |
| 标签 6 个（材料特征） | 实际 9 个且语义域混杂 | **受控词表分层**（大纲层级 / 命题信号 / 教学标记 / 题型） |
| 单选 `priority` = ★/●/○ | 考研同时存在「大纲掌握层级」与「命题频度」两轴 | `priority` 保留为**排序唯一驱动**；`tags` 承载其余维度 |

## 三、拟采用的标准元数据框架

### 3.1 层级模型

```
科目 subject（101 / 204 / 315 / 812）
└── 模块 module（二级，受控；如 101 马原、315 有机化学、812 植物生理学、204 阅读理解）
    └── 章节 chapter（权重中心 / 区间 / 梯队在此层）
        └── 知识点 point（最小记忆单元，唯一行粒度）
            ├── 学习单元 unit[]（LLM 派生，1:N，身份 = (point_id, idx)）
            ├── 背题卡 cards[]（人工产出，1:0~4）
            └── 题目 quiz[]（人工产出，1:0~N）
```

**模块层**是本次新增的一层。理由：101 的「马原/史纲/习概」、315 的「无机化学/有机化学」在现有数据里是真实存在的二级归类（101 已有 `chapter.tags=['马原']`；315 虽未落库，但 26 章天然分 11+15 两块），而 204/812 缺失。统一显式建模后，四科层级才可比。

### 3.2 章节级字段（10 个）

| # | 字段 | 类型 | 必填 | 取值规则 | 示例 |
|---|---|---|---|---|---|
| C1 | `chapter_id` | 文本 | 是 | `^(101\|204\|315\|812)-\d{2}$`，全局唯一 | `812-02` |
| C2 | `subject` | 枚举 | 是 | 4 科 | `812` |
| C3 | `module` | 文本 | 是 | 受控，见 §3.4 | `植物生理学` |
| C4 | `chapter_name` | 文本 | 是 | 完整章名 | `第二章 植物的水分代谢` |
| C5 | `order` | 整数 | 是 | 章内 0..N-1，**连续无空洞** | `2` |
| C6 | `tier` | 枚举 | 是 | `1`/`2`/`3`（第 1/2/3 梯队） | `2` |
| C7 | `weight_center` | 数值 | 是 | 权重中心分，≥0 | `13` |
| C8 | `weight_range` | 区间 | 否 | `[min,max]`；无推算依据时留空 | `[9,17]` |

**priority 判定规则**（消解多标签歧义；章级 + 点级双输入，修订依据见 §5.5）：

```
1. 若 chapter.tier == 1  或  tags 含 {高频, 常考, 必掌握, 重点}   → ★
2. 否则若 tags 含 {易错}                                          → ●
3. 否则                                                          → ○
```

> 采用双输入的原因：101 与 204 的 `tags` 大面积为空（119/155、51/51），纯按 tags 判定会使两科 priority 全部退化为 `○`，失去排序意义。

**权重来源 weight_basis**：`官方`（大纲原文给出的分值）／`推算`（权重报告推算区间）／`人工估计`（无调研依据，如 204）。

#### 3.5.1 TTS 元数据（「听」视图的输入）

后续应用将基于本元数据重建，只保留 **听 / 记 / 看** 三个视图。因此元数据层必须自带「听」所需的全部信息，使后续项目无需回头读取 kaoyan-system。

| 字段 | 类型 | 说明 |
|---|---|---|
| `tts.enabled` | bool | 是否可听。204 全科为 `false`（无音频方案）；其余为 `true` |
| `tts.max_chars` | int | 朗读段最大字符数，默认 `220`（≈ 42 秒） |
| `tts.est_sec` | number | 整点预估时长秒数 |
| `tts.clips[]` | 数组 | `[{clip_id, text, est_sec}]`，切分后的朗读段 |
| `clip_id` | 文本 | 单段时 = `point_id`；多段时 = `{point_id}-p{i}`（沿用现有约定） |

**朗读文本生成规则**（沿用 `scripts/normalize.py:77-94` 的 `to_speech`，本项目内复刻）：

| 规则组 | 示例 → 输出 |
|---|---|
| 化学式 | `H₂O` → `氢二氧`；`CO₂` → `二氧化碳` |
| 离子 | `Na⁺` → `钠离子`；`SO₄²⁻` → `硫酸根离子` |
| 缩写/专名 | `ATP` → `A T P`；`DNA` → `D N A` |
| 希腊字母/符号 | `Δ` → `德尔塔`；`α` → `阿尔法`；`≈` → `约等于` |
| 箭头（**按科目分流**） | 315：`→` → `生成`；812/默认：`→` → `到` |
| 数字区间 | `9-17` → `9 到 17` |
| 分隔符 | `；` → `。` |
| 清理 | 去 `*` `#` 反引号，空白归一 |

> ⚠️ 箭头规则的科目分流必须保留——旧代码 `merge_fragment_points.py:56` 曾把 subject 硬编码为 `"812"`，是潜在缺陷。

**时长预估口径（实测）**：基于 812 现有 107 条真实音频统计，字/秒 **中位 5.22**、均值 5.60（区间 3.80–18.57）。取 **5.2 字/秒** 作为预估系数（偏保守，时长估高）。

| 朗读段字数 | 预估时长 |
|---|---|
| 30 字 | ≈ 5.8 秒 |
| 90 字 | ≈ 17.3 秒 |
| 220 字 | ≈ 42.3 秒 |

**分段规则**（沿用 `normalize.py:101-133` 的 `split_clips`）：按句界 `。！？!?` 切；单句超限则按 `，,、` 软切；仍超限则硬切。

### 3.7 溯源定位符规范（本次核心新增）

定位符格式：`section#unit路径`

| 科目 | 格式 | 示例 |
|---|---|---|
| 812 | `p4-2#chapter[N]/p[0]/split[M]` | `p4-2#chapter[1]/p[0]/split[1]` |
| 812 机制点 | `p4-2#chapter[N]/mech[0]` | `p4-2#chapter[1]/mech[0]` |
| 315 | `p3-4#topic[N]/p[0]/split[M]` | `p3-4#topic[0]/p[0]/split[1]` |
| 101 | `p1-4#topic[N]/p[0]/split[M]` | `p1-4#topic[0]/p[0]/split[0]` |
| 204 | `manual:CHAPTERS_204[N].texts[M]` | `manual:CHAPTERS_204[1].texts[0]` |

N/M 均为 0 基下标。

**抽取配方（必须严格按此顺序，否则结果不一致）**：

```
1. 定位 <section class="section" id="{section}">
2. 按容器切块：812 → <div class="chapter">；315/101 → <h3> 起始的 topic 块
3. 取块内第一个无 class 的 <p>（排除 <p class="small"> / <p class="mech">）
4. 剥标签 → HTML 实体反转义 → 空白归一
5. 按 [；;] 切分
6. 长度 <5 的碎片并入前一片（用 ；连接）
7. 下标 M 从 0 开始
```

**可行性已实测**：用该配方从 HTML 重建 812/315/101 全部知识点，与 `content.json` 逐字比对：

| 结果 | 数量 | 说明 |
|---|---|---|
| 逐字完全一致 | **449 / 460** | 97.6% |
| 差异（因片段被合并） | 8 | 812-02-04、812-02-08、812-07-01、812-07-03、812-07-06、812-09-04 等，均为 `merge_fragment_points` 的合并产物 |
| 无定位符（手工补入） | 3 | 315-13-10、315-19-07、315-20-14 |

结论：**定位符方案可行**，且 8 例差异 + 3 例例外恰好由 `merged_from` 与 `source.type=manual` 两个字段承载。

### 3.8 校验规则（E 码阻断 / W 码警告）

**硬错误（阻断定稿）**

| 码 | 规则 |
|---|---|
| E01 | 表头与规范表头不一致，或列数不符 |
| E02 | `id` 格式错 / 全局重复 / 前缀与科目不符 / **号段有空洞** |
| E03 | `chapter_id` 在章节表中不存在 |
| E04 | 必填字段为空（含 `explain`/`exam`/`rationale`/`locator`/`title`；`legacy_id` 已降为可选，不再必填） |
| E05 | 字段长度越界（`point`>90 字 / `title`>14 字 / `note`>80 字 / `explain` 非 3–6 句） |
| E06 | `priority` ∉ {★,●,○}；`tags` ⊄ 受控词表或 >3 个 |
| E07 | `locator` 无法解析到源文件，或解析结果与 `point` 文本不一致 |
| E08 | `legacy_id` 重复（若填写）；`id` 与 `legacy_id` 混用（不得用旧 id 做主键） |
| E09 | `sources` 不可解析为 `类型:文件#定位` 三元组 |
| E10 | front matter 缺失，或 `status` ∉ {draft, final} |
| E11 | `entry_count` 与本章实际行数不符 |
| E12 | `priority` 与 `tags` 冲突（如 `★` 却含 `了解`） |
| E13 | `module` ∉ 受控词表（该科目） |

**软警告（人工复核，不阻断）**

| 码 | 规则 |
|---|---|
| W01 | 同一章内 `point` 文本完全重复（疑似撞车） |
| W02 | `title` 在同一科目内重复 |
| W03 | 跨章 `point` 文本重复（同一考点在多章出现） |
| W04 | `title` 含答案性表述（泄题风险） |
| W05 | 无卡片派生的知识点（未接入学习卡） |
| W06 | `weight_range` 为空且 `weight_basis` 非 `人工估计`（缺推算依据） |
| W07 | `card.kind` 为空（对应现 50 张缺 kind 的卡） |

### 3.9 特殊情况处理规则（核心原则：标记而不猜测）

| 情况 | 处理规则 |
|---|---|
| **重复知识点**（同章内） | 不合并。两条独立保留，第二条加 `note` 标注「与 XXX 疑似重复，待人工裁定」，同时产出 W01 |
| **重复知识点**（跨章） | 不移动、不合并。各自保留，`related` 关系写入 `note`，产出 W03 |
| **跨章节知识点** | 保持在其权重所属章；如需跨章引用，写入 `note` 的「关联考点」段，不建父子指针 |
| **知识点拆分**（一句含多考点） | 拆为多条，新 `id` 连号分配；原 `locator` 记入 `merged_from`（反向：拆分来源记 `note`）；被拆出的旧 id 可记入 `legacy_id`（可选） |
| **知识点合并**（括号不闭合的碎片） | 合并为一条，`merged_from` 记全部原 `locator`；被合并旧 id 可列入 `legacy_id`（可选） |
| **缺失字段** | 一律填 `待补` 并进问题清单，**不得**用推测内容填充 |
| **无法确定归属的章** | 保留原章，`module` 填 `待定`，进问题清单 |
| **权重无依据** | `weight_basis` 填 `人工估计`，`weight_range` 留空，产出 W06 |
| **脱离 HTML 的手工条目** | `locator` 填 `manual:<来源说明>`，`source.type=manual`，产出 W05 |
| **知识点 id 空洞** | 新框架按 `order` 连续重编，`id` 号段连续；旧号可记入 `legacy_id` 保留可追溯（可选字段） |

### 5.2 共性（可统一）

1. **层级同为 3 级**：科目 > 章 > 知识点，章层均承载 权重/梯队/标题。
2. **知识点粒度一致**：均为「HTML 段内分号切分」（204 例外，为常量表）。
3. **卡片体系一致**：均为「知识点 → 卡片」的 1:N 弱关联，均以 `point_id` 挂靠，均无独立映射表。
4. **派生层一致**：`unit` 由 LLM 从讲解拆分（6–12 条/点），无独立 id，身份为 `(point_id, idx)`。
5. **溯源缺口一致**：四科均无法从知识点反查原始文档位置。

### 5.4 最终标准框架建议（结论）

**核心 25 字段（10 章节级 + 15 知识点级）全科目统一，科目差异一律进扩展字段。**

四条落地原则：

1. **溯源优先**——`locator` + `merged_from` + `sources` 三件套是本次框架相对现状的最大增量，使每个知识点都能反查回原始文档的具体分句位置。
2. **md 人审 / JSON 机洗单向流水线**——沿用法考框架，杜绝两套数据漂移。
3. **标签受控 + priority 单一驱动**——排序只看 `priority`，其余维度进 `tags`；`tags` 强制受控词表校验。
4. **标记而不猜测**——缺失、冲突、不确定一律进问题清单，不静默填充、不静默删除。
5. **自包含三视图**——后续应用只保留 **听 / 记 / 看**，元数据层必须自带三视图所需全部输入：听靠 `spoken` + `tts`（§3.5.1），记靠 `units` + `cards` + `priority`/`tier`，看靠 `explain`/`exam`/`keywords`/`title`/`media`。**不依赖 kaoyan-system 的任何既有文件。**

### 5.5 建议的 priority 判定规则（修订版）

初版规则（仅看 tags）在 101/204 上失效——两科 `tags` 大面积为空，导致 priority 全为 `○`，失去排序意义。修订为**章级 + 点级双输入**：

```
1. 若 chapter.tier == 1  或  tags 含 {高频, 常考, 必掌握, 重点}   → ★
2. 否则若 tags 含 {易错}                                          → ●
3. 否则                                                          → ○
```

按此规则重算（预估）：812 有 3 个 tier1 章 + 45 个「重点」点；315 有 7 个 tier1 章 + 122 个「必掌握」点；101 有 15 个 tier1 章；204 有 3 个 tier1 章。四科的 priority 分布均恢复区分度。
